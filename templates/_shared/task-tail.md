# 反例（这些都算失败）

- 戴镣铐：草稿只说「那个插件超时太短了，调一下」，却输出「最小改动，不重构无关代码，改完先问我」——用户从没这么说，这是在砍助手的手脚。
- 角色卡：输出 "# Role: 超时配置专家 / ## Profile / ## Skills…"——这是给助手一份人设，不是一个任务。
- 编造现象：输出「现象：请求登录接口返回 403，cookie 未写入」——草稿从没说过 403。
- 待确认变门槛：输出「开始前请先提供以下信息：…」——助手会停在那里不干活。
- 效果空转：草稿说「页面太卡了，给整快点」，输出只写「提升页面性能」——感受词被原样复制，没有落到"关键操作等待明显变短"这种可验收效果。
- 发明指标：草稿没给数字，输出「P95 延迟降到 200ms 以内」——这是编指标，应该写待确认。
- 抢选择权：草稿说「你看着办」，输出却写「采用方案 A，不要用其他方案」——把用户给助手的授权收走了。
- 缺项：草稿是「帮我写个压测脚本，要能跑」，输出只写「写一个可运行的压测脚本」——没有完成标准、没有交付，助手只能猜你要什么算做完。
- 软词：约束写成「尽量不要影响现有功能」「最好用现成方案」——"尽量 / 最好"会被模型降级成可选项，等于没约束；要么写成硬约束，要么删掉。
- 编造约束：草稿只说「把这个页面改好看点」，输出却写「不要动其他页面、不要改数据结构」——草稿没说的范围限制同样是凭空发明，和戴镣铐一样算失败。
- 长句堆约束：把「接口不能变、错误码要保持、日志格式别改、性能不能降」塞进一句话——模型会漏读后半句；必须一条一行、一行只约束一件事。

# 正例

草稿：帮我看下签到脚本为什么登录失败，修一下

输出：
定位签到脚本登录失败的根因并修好，做完告诉我根因、改了哪里、怎么验证的。
完成标准：脚本能正常完成登录，原来的登录失败不再出现。
交付：根因说明 + 改动位置 + 复测结果。
待确认（可先按合理默认推进，做完说明用了什么默认）：
- 脚本路径与运行方式
- 失败时的报错或响应原文
以实际复测结果为准，不要用推测代替验证。

草稿：这页面太卡了，给整快点

输出：
把页面卡顿修到可感知的流畅：打开、滚动、提交这些关键操作等待明显变短，且现在的卡顿不再复现。
约束：
- 只处理这个页面的卡顿，不扩大到其他页面或整体性能改造。
- 修完后现有功能保持可用，不因这次改动出现新的异常。
完成标准：按出现卡顿的操作路径逐项复测，等待明显变短、没有新的报错。
交付：根因、改了哪里、怎么验证的。
待确认（可先按合理默认推进，做完说明用了什么默认）：
- 卡顿出现的页面与操作路径
- 可接受的性能目标（没数字就按"明显变流畅"验收）
以上述可观察效果为验收标准，不要用估算数值代替实际复测。

草稿：登录页那个报错修一下，别再犯了

输出：
修好登录页现有的报错：登录流程能正常走完，现在的报错不再出现。
已知：登录页存在报错，需要修好。
约束：
- 只处理登录页这个报错，不扩大到其他页面的改造。
- 修完后登录流程保持可用，不因这次改动出现新的异常。
完成标准：按原来的操作路径复测，登录能正常完成、原报错不再出现。
交付：根因说明 + 改动位置 + 复测结果。
待确认（可先按合理默认推进，做完说明用了什么默认）：
- 报错原文与复现步骤
- 出现问题的环境（本地 / 线上）
以复测结果为准，不要用"应该好了"这类推测代替验证。
