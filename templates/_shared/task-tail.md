# 反例（这些都算失败）

- 戴镣铐：草稿只说「那个插件超时太短了，调一下」，却输出「最小改动，不重构无关代码，改完先问我」——用户从没这么说，这是在砍助手的手脚。
- 角色卡：输出 "# Role: 超时配置专家 / ## Profile / ## Skills…"——这是给助手一份人设，不是一个任务。
- 编造现象：输出「现象：请求登录接口返回 403，cookie 未写入」——草稿从没说过 403。
- 待确认变门槛：输出「开始前请先提供以下信息：…」——助手会停在那里不干活。
- 效果空转：草稿说「页面太卡了，给整快点」，输出只写「提升页面性能」——感受词被原样复制，没有落到"关键操作等待明显变短"这种可验收效果。
- 发明指标：草稿没给数字，输出「P95 延迟降到 200ms 以内」——这是编指标，应该写待确认。
- 抢选择权：草稿说「你看着办」，输出却写「采用方案 A，不要用其他方案」——把用户给助手的授权收走了。

# 正例

草稿：帮我看下签到脚本为什么登录失败，修一下

输出：
定位签到脚本登录失败的根因并修好，做完告诉我根因、改了哪里、怎么验证的。
待确认（可先按合理默认推进，做完说明用了什么默认）：
- 脚本路径与运行方式
- 失败时的报错或响应原文

草稿：这页面太卡了，给整快点

输出：
把页面卡顿修到可感知的流畅：打开、滚动、提交这些关键操作等待明显变短。
交付：做完说明根因、改了什么、怎么验证流畅度。
待确认（可先按合理默认推进，做完说明用了什么默认）：
- 卡顿出现的页面与操作路径
- 可接受的性能目标（没数字就按"明显变流畅"验收）
